# TV3 — Uncertain Checkout outcome reconciliation runbook

**Safety rule:** never automatically release inventory or unlock Cart after timeout unless committed outcome is verified.

1. Lookup checkout_attempt by (customer_id,idempotency_key), record attempt.id and state.
2. Use attempt.id as the deterministic Order ID and **correlation ID only**. TV4 Inventory uses distinct, stable step-level `operationId` values for RESERVE, RELEASE and CONSUME; never reuse one operationId across types. Current TV3 InventoryPort still accepts orderId/productId and is **not** a compatible live adapter.
3. If a placed Order exists, do not release stock: verify SellerOrders/outbox, repair attempt state transactionally with TV4/DB owner review, and finalize the Cart idempotently.
4. If no Order exists, Inventory RESERVE may still have committed. The **proposed, not implemented** Order journal must commit the exact canonical SKU/positive long quantity line set, operation type and stable step-specific operationId **before HTTP** (short local T1), then persist the outcome separately (T2). On timeout, TV4 permits a **bounded retry of precisely that persisted operationId + type + payload**: Inventory ledger returns a replay for a prior commit, or applies the operation once if not committed. No first-stage status lookup endpoint is required by TV4 for this retry proposal. A timed-out retry is still an **unknown** outcome; never generate a different operationId, invent `release(orderId)` or compensate stock blindly.
5. Stale PROCESSING is marked NEEDS_RECONCILIATION by a scheduled scanner. It does NOT modify remote services.
6. When the approved retry window/attempt budget is exhausted without a definitive response, keep the attempt under NEEDS_RECONCILIATION/manual hold and alert operations; do not auto-release/consume. Retry budget, backoff, SLA and authoritative Order/SellerOrder event boundaries are **not yet approved**. If the local DB is unavailable, do not fabricate persisted intent or remote outcome.
7. Document operator, external evidence, outcome, timestamps, and manual state transitions. No unreviewed direct SQL correction.

**Production remains blocked** pending TV2 authoritative Product→SKU/Store mapping, TV5 Finance/COD approval, TV3 durable journal + bounded retry implementation, TV3/TV4/TV5 SellerOrder dispatch/return lifecycle agreement, TV1 service authentication, and real live crash/retry/E2E evidence. TV4 does not require a new status lookup for initial exact-idempotent retry, but long-lived unknown outcomes still need manual hold/alert.

TV5 regression fix: stale scanner and uncertain-failure marking use conditional DB UPDATEs restricted to PROCESSING. A concurrently committed SUCCEEDED row is retained. Successful replay and committed-outcome reads load the response collection with the verified customer's ID scope before returning from the repository. These guards do not perform remote compensation or replace the operator-led steps above; see TEST_RESULTS_TV5_FIXES.md for real PostgreSQL race/replay tests.
