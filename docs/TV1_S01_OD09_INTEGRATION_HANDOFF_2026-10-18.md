## 1. S01 — Store data ownership and trusted actor (TV1 security/architecture decision)

**TV1 DECIDED within its responsibility**: accept TV2's proposed **Store in `seller-service` using Seller DB** for COD MVP. The Store table belongs to the Seller database/migrator, with a *same-database* restrictive FK `stores.seller_id → seller_profiles.id`, a unique `seller_id` (one Store per Seller for MVP), globally unique canonical lowercase slug, Store UUID PK, and explicit persisted open/closed status. Product persists only a logical **Store UUID** in its own DB; **no cross-database FK or SQL JOIN**. Do not copy Seller account ownership from untrusted HTTP into a Store as independent authority. Existing `store_candidate` SQL and tests are **test-only**; TV2 must author a new, reviewed Flyway V2+ and JPA/constraints; never rewrite applied V1.

**Identity boundary:** Auth JWT `sub` is an opaque stable *account reference string* from a cryptographically verified token; it is **not** `sellerId`, `storeId`, or `productId` and is not parsed/coerced by TV2 consumers. TV2 binds `SellerIdentity(reference=sub)` *only inside its verified security adapter*, resolves Seller profile by its server-owned `owner_reference`, then Store by authoritative local Seller FK. Store/Seller/Product domain UUIDs retain their own canonical identifier contract; no provider may derive `storeId` or `sellerId` from a client header/claim. Do not permit arbitrary `ownerReference` from request payloads or external events to authorize changes.

**Current authorization rules (deny by default):**
- Registration/application: authenticated CUSTOMER may apply to Seller; role SELLER is **not** a prerequisite to apply. Auth owns role grants, TV2 owns Seller status; role update/grant requires an authenticated, idempotent and versioned **Seller→Auth** system command *after* Seller transaction commit, with durable retry/ordering. No FE-created role grants.
- Store create/edit/open/close and Product mutation: verified actor must be the **exact current owner** of the Seller, Seller is **currently APPROVED**, relevant Store is open when the operation requires it, and its Store→Seller mapping matches the targeted record. A JWT `SELLER` role alone (including stale tokens after suspension) is insufficient. For initial Store creation, use verified approved Seller as source even though a Store does not yet exist.
- Seller/Product moderation, privileged House assignment and COD confirmation require verified **current ADMIN** plus any business/domain guards; never infer current admin state from role claim alone. No self-moderation; ADMIN does not automatically get other users' Store data.
- Store/Seller/product current-state dependency missing, stale, conflicting or unverifiable → **503 fail-closed**, never 'allow' or substitute fixture/header; verified unauthorized actor → **403**, missing/invalid actor → **401**. Do not turn 'dependency unavailable' into 'product not found'.
- For multi-Store Checkout, TV2 returns authoritative Product→SKU and current Product/Store/Seller facts from trusted providers; Product owns **immutable globally unique exact SKU** as target, Inventory remains SKU-keyed and `productId != sku`. Data used in Cart expectations and request fields is comparison-only. No price/House override from JWT, customer or Store slug.

**Intentionally still pending:** TV2 product/store production persistence and API; actual House classification/privileged assignment mechanism; existing-order fulfillment policy after Seller SUSPENDED/Store closed; recipient/contact data scope; final Catalog wire/freshness; business MD07 acceptance; positive service auth; tests with real JWT+DB. These cannot be signed on behalf of TV2, TV4, TV5 or the business owner. A Seller FK only proves relationship, not current eligibility.

**TV2 may start now:** scoped `seller-service` Store Flyway V2+/entity/repository and local, concurrency/uniqueness/ownership tests; create a trusted read adapter for *current* Seller/Store facts, plus deny-default HTTP security tests. Keep all privileged positive endpoints closed until the specific caller/callee security contract is implemented and tested. TV3/TV4 may write authorization/consumer negative tests and mocks against this model. Ask TV2 to reply `S01 TV2: CONFIRMED|REVISE` with exact schema/provider SHA; TV3/TV4 separately acknowledge current Store authority.

## 2. OD-09 — TV1 approved service security baseline and pair matrix

The existing `docs/TV1_AUTH_IDENTITY_GATEWAY_CONTRACT.md` OD-09 remains authoritative: `/internal/**` must **never** be forwarded by public Gateway; distinct cryptographically random opaque `X-Internal-Token` per caller→callee *pair*, separate from HS256 signing secrets, constant-time comparison, current+previous credentials for controlled rotation. No caller-selected `X-Service-Name`, `X-User-Id`, `X-Store-Id`, `X-Roles`, body seller/customer IDs or forwarded headers become identity. The downstream/callee performs method + **exact path** + **operation** scope checks. Unknown/unconfigured credential denies access, not `permitAll`: invalid/missing pair **401 `INTERNAL_AUTH_INVALID`**, valid pair/wrong route or operation **403 `INTERNAL_FORBIDDEN`**, unavailable trusted verification **503**. Access JWT failure uses Auth's separate 401/403 semantics.

**TV1 security allowlist intent v1** (a *design authorization* for implementation/tests, **not** evidence that endpoints or per-pair filters currently exist):

| Pair | Allowed method/path and operation | Delegation / authority check | Provider/runtime gate |
|---|---|---|---|

**Privacy/error rule:** for an authenticated Catalog batch, `200` with complete all-ready evaluation or all snapshots withheld on a rejected batch is an *existing owner proposal*, not a live endpoint. Missing/stale/incomplete/unverifiable provider facts → `503`, not Product-not-found; only trusted confirmed absence may map to `PRODUCT_NOT_FOUND`. No `ownerReference`, phone, Seller moderation reason, secret or price of unavailable lines leaked to unentitled callers. For unauthorized cross-Store SellerOrder read/mutation, no data leak and deny according to the signed endpoint's 403/concealment policy; never expose by guessed owner claims. Exact error envelope and challenge to be confirmed TV1+callee+consumer.

**Secret + network rule:** configure environment-specific secrets in runtime secret channels only; do not commit/copy/sample real tokens in docs, logs or tests. Do not give user JWT HS256 signing keys as internal tokens. Strip client-supplied `X-Internal-Token` at Gateway and never CORS-expose it. Private downstream networking is defense-in-depth; the callee **must** still validate pair scope.

**Required tests (not yet executed):** wrong/missing pair 401; cross-pair token 401; correct pair/wrong method/path/type 403; missing verifier/role/current-status source 503; replay/rotation current+previous→retire; user JWT alone cannot access internal APIs; client-forged `X-User-Id`/`X-Store-Id` ignored; stale SELLER/ADMIN rejected; customer A cannot claim/release B's Cart; Order pair cannot initialize/increase/decrease stock; no wildcard or public Gateway route; request payload's actor/owner cannot override verified principal. Run positive Auth-issued JWT and scoped pair tests only after the actual filters are implemented. Record exact source SHA and PASS/FAIL/NOT_RUN.
